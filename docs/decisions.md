## 2026-02-28: 意思決定の記録方法を決定

- **背景:** フェーズ移行や設計判断を記録する手段が必要だった。選択肢として、ADR（1決定1ファイル）、単一ログファイル、git コミットログのみ、の3つを検討した
- **決定:** `docs/decisions.md` に時系列で追記する方式を採用。フェーズの進捗状況は `docs/process.md` のチェックリストで管理し、役割を分担する
- **理由:** 個人開発の頻度（週数回）では1決定1ファイルの ADR は摩擦が大きい。単一ファイルなら開けば全決定を一覧でき、肥大化の心配も当面ない。git コミットログだけでは「今どういう判断に基づいて進んでいるか」の一覧性がない

## 2026-03-05: 企画・設計フェーズのステップ構成を修正

- **背景:** ニーズ整理完了後、ユーザーストーリー → 優先順位 → 技術選定・設計 → 実装、という直列の計画を立てたが、批判的に再検討した結果、いくつかの問題が見つかった
- **問題点:**
  1. 「技術選定・設計」ステップにデータモデル・画面構成・技術スタックが混在しており、性質の異なる検討が雑居していた
  2. 画面構成・操作フローの検討が完全に欠落していた。記録・検索アプリでは「どんな画面でどう操作するか」がないと受け入れ条件も実装も具体化できない
  3. ユーザーストーリーの受け入れ条件を設計前に確定させる順序になっていたが、具体的な条件を書くには画面やデータ構造の概念が必要（鶏と卵の問題）
  4. URL メタデータ自動取得の技術的実現可能性の検証が抜けていた
- **決定:** ステップ構成を以下のように修正した
  1. ユーザーストーリー作成（ラフ。受け入れ条件は仮置き）
  2. ストーリーの優先順位づけ・MVP 範囲決定
  3. 設計（3つのサブステップ: データモデル / 画面構成・操作フロー / 技術スタック選定）
  4. 受け入れ条件の具体化（設計を反映してストーリーを仕上げる）
  5. タスク分解・実装
- **理由:** データモデルと画面構成は「何を作るか」の具体化、技術スタックは「どう作るか」の話であり、分けて扱うべき。また、設計結果をストーリーにフィードバックするステップを明示することで、鶏と卵の問題を解消する。個人開発なので正式なワイヤーフレームや API 設計書は不要だが、データモデル・画面構成・技術リスクの検証は明示的に行う

## 2026-03-15: テーブル分割（Song + Encounter）を不採用。単一テーブルを維持

- **背景:** 同じ曲への再遭遇を記録したいというニーズから、曲テーブル（songs）と遭遇テーブル（encounters）に分割する案を検討した
- **決定:** 分割せず、単一の records テーブルを維持する。同じ URL での再記録を許可する（URL に一意制約なし）
- **理由:**
  1. 「同じ曲」をシステムが同定できない。即時キャプチャでは URL のみで title/artist は空。URL も同じ曲の別動画（ライブ版、転載等）があり、信頼できる識別子にならない
  2. MVP の CRUD が複雑化する。S1（記録）が「既存 song の確認→分岐」を伴い、即時キャプチャの「さっと保存」体験に摩擦が生まれる
  3. タグやメモが song と encounter のどちらに属するか曖昧になる
  4. 一覧表示（S4）で表示単位（曲 or 遭遇）と集約の問題が発生する
  5. 再遭遇は週数回の記録に対してさらに稀。稀なケースのために全体を複雑にするのは過剰
- **再遭遇への対応:** UI 側で解決する。URL 入力時に既存レコードがあれば通知する程度で十分（単純な SELECT で実現可能）

## 2026-03-15: デプロイ形態をローカル実行に決定

- **背景:** 設計フェーズの第1段階として、デプロイ形態を決める必要があった。選択肢は A（ローカル実行）と B（ホスティング）
- **決定:** A（ローカル実行）を採用。軽量サーバー + SQLite で構成する
- **理由:**
  - 個人用・単一 PC なのでホスティングのインフラ管理・コストが不要
  - 軽量サーバー（Go や Node）+ SQLite なら起動は数百ミリ秒。使いたいときにすぐ起動できる
  - メモリ消費もごくわずか（数十 MB 以下）
  - ネットワーク不要でオフラインでも動く
  - 将来ホスティングに移行したくなった場合も、データモデルや画面はそのまま使える（DB とデプロイだけ変える）
- **常駐方式について:** バックグラウンド常駐（スタートアップ自動起動）は不採用。ユーザーの管理スタイルに合わない。使いたいときに起動し、使い終わったら終了する運用とする。軽量サーバーなら起動は数百ミリ秒〜1秒程度で、即時入力の要件を満たせる
- **移行トリガー:** 「スマホからも記録したい」が現実になったとき

## 2026-03-15: タグの保存方式を別テーブル（中間テーブルなし）+ 正規化に決定

- **背景:** タグは Record に複数付与可能。保存方式として JSON 配列、カンマ区切り、別テーブル（中間テーブルあり/なし）の4案を比較検討した。また、タグの「自由に入力したい」と「確実に見つけたい」の緊張関係（Recall vs Precision）をどう解消するかが論点になった
- **決定:**
  1. 保存方式: 別テーブル（`tags` テーブルに `record_id` + `name`）。中間テーブルなし
  2. 正規化: 保存時に trim → NFKC → lowercase を適用（後に日本語対応で NFKC を追加。詳細は「日本語テキスト対応方針」エントリ参照）
  3. 入力時の既存タグ候補表示は S7（タグ検索）と合わせて次期で実装
- **理由:**
  - JSON 配列やカンマ区切りはMVP実装が最小だが、次期の S7（タグ検索）で構造変更が必要になる。テーブル1つ増えるだけで実装コスト差は小さく、移行コストを回避できる
  - 中間テーブル付きの完全正規化（タグマスタ）は個人ツールには過剰。タグの利用頻度集計等のニーズがない
  - 正規化（lowercase + trim）で表記ゆれの大半を自動吸収し Recall を確保。Precision は完全一致で維持
  - 候補表示はさらに Recall を補強するが、画面実装が必要なため MVP では見送り

## 2026-03-15: 検索方式を完全一致 + FTS5 に決定。ベクトル検索は不採用

- **背景:** 次期の検索機能（S5〜S7）に向けて、検索の技術方式を検討した。タグ検索（短い単語の一致）とメモ検索（自由テキスト）の性質の違い、および BM25 やベクトル検索（LLM 埋め込み）の要否を評価した
- **決定:** タグは正規化済み完全一致、メモ・アーティスト名・曲名は SQLite FTS5。ベクトル検索は不採用。（トークナイザは後に日本語対応で trigram に決定。詳細は「日本語テキスト対応方針」エントリ参照）
- **理由:**
  - タグ: 正規化 + 完全一致で Recall/Precision 両方カバーできる。類似度検索は不要
  - メモ: FTS5 は SQLite 組み込みで追加依存なし。BM25 ランキングも内蔵
  - ベクトル検索を不採用とした根拠:
    1. 検索対象テキストが短すぎる（ひとことメモ、単語タグ）。埋め込みの精度が出にくい
    2. レコード数が少なすぎる（年間数百件）。全件走査で十分
    3. 意味的類似による検索結果の Precision が個人の音楽記録で有用か不明
    4. ローカル実行と決めたのに埋め込みモデルの管理が増え、軽量さと矛盾する
    5. 「雰囲気で探したい」というニーズが現時点で挙がっていない
- **再検討トリガー:** レコードが数千件に増え、かつ意味的検索のニーズが実際に発生したとき。埋め込みカラムの後付けは容易

## 2026-03-15: 日本語テキスト対応方針を決定

- **背景:** ユーザーは日本人で、聴く音楽も日本のものが多い。アーティスト名・曲名は日本語（漢字・ひらがな・カタカナ・ローマ字の混在）、メモはほぼ日本語。この制約が検索方式とタグ正規化の設計に影響する
- **影響1 — FTS5 トークナイザ:** デフォルトの unicode61 トークナイザは空白分割のため、分かち書きしない日本語を正しく検索できない
- **決定1:** FTS5 の trigram トークナイザを採用
- **理由:**
  1. 分かち書き不要で日本語テキストを部分文字列マッチとして検索できる
  2. SQLite 3.34.0 以降に組み込み済みで追加依存がない（ICU 拡張や MeCab が不要）
  3. 日英混在テキストでも問題なく動作する
  4. 最小クエリ長3文字の制約があるが、日本語の実用的な検索語は3文字以上が大半。短いクエリは LIKE フォールバックで対応可能
  5. BM25 ランキングが使えなくなるが、レコード数が少なくランキングの重要度は低い
- **不採用案:**
  - ICU トークナイザ: ICU ライブラリへの依存が増え、ローカル実行の軽量さと矛盾する
  - MeCab 等の形態素解析器: 辞書管理が必要で個人ツールには過剰。固有名詞（アーティスト名）の未知語問題もある
- **影響2 — タグ正規化:** lowercase + trim だけでは全角/半角の表記ゆれを吸収できない
- **決定2:** タグ保存時の正規化に NFKC 正規化を追加（trim → NFKC → lowercase の順）
- **理由:**
  - NFKC は全角英数 → 半角（`Ｊａｚｚ` → `Jazz`）、互換文字の統一を行う。Unicode 標準の正規化形式で、多くの言語ランタイムに組み込み済み
  - カタカナ ↔ ひらがなの変換は行わない。「ジャズ」と「じゃず」は意味的ニュアンスが異なり、自動変換はユーザーの意図を損なうリスクがある
  - 長音の揺れ（`サーバー`/`サーバ`）やカタカナ表記の揺れは、入力時の候補表示（次期 S7）で対応する方が適切。保存時の自動変換は予測困難な副作用が大きい
- **再検討トリガー:** 運用開始後に日本語テキストの検索や表記ゆれに関する不満が実際に発生したとき。具体的な既知の限界と対応方針は [design.md の「日本語対応の既知の限界と再検討トリガー」](design.md) に記載。現設計は「追加依存なし・軽量」を優先した判断であり、摩擦が顕在化した時点でユーザーストーリーやバックログの更新を経てアーキテクチャを見直す

## 2026-03-15: ステップ移行時レビューに問0（整合性検査）を追加

- **背景:** 優先順位づけの過程で、S1・S2 の部分更新を行った。AI がドキュメントを部分更新する際、直前の対話を過度に重視して全体の整合性が崩れるリスクがあることをユーザーが指摘した
- **決定:** ステップ移行時レビューに問0「成果物の整合性は保たれているか？」を追加。問1（クライテリア検査）の前提として、ドキュメント内の一貫性・構成の粒度、およびドキュメント間の矛盾・齟齬がないかを確認する
- **理由:** 既存の問1〜問3はいずれもこの観点をカバーしていなかった。全ステップ移行に共通する検査であるため、各ステップのチェックリストではなくレビューの共通手順に配置する。プロセス原則の「手戻りを減らすこと」に直結し、「過剰な管理をしない」原則とも矛盾しない（ドキュメントが少量の現時点では確認コストが低い）

## 2026-03-20: 画面構成・操作フロー（4b）の検討方法を決定

- **背景:** 設計の第2段階に着手するにあたり、画面構成・操作フローをどのような方法で検討するかを整理した。候補として、画面一覧+遷移図（テキスト）、ASCII ワイヤーフレーム、シナリオウォークスルー、選択肢提示型の4つを比較した
- **決定:** **シナリオウォークスルー + 構造の要約** の2段階で進める
  1. MVP の各ストーリーを「ユーザーが実際に使う場面」として時系列で歩き、各ステップで「何が見えるか」「何をするか」を具体的に描写する。区切りごとにフィードバックを得る
  2. 全シナリオ完了後、浮かび上がった画面と遷移を構造として整理する
- **理由:**
  - シナリオは自分の行動として想像できるため、抽象的な画面仕様より判断しやすく、理解の摩擦が低い
  - 「ここは違う」「こうしたい」が自然に出やすく、情報提供の摩擦も低い
  - 最後に構造を整理することで、シナリオだけでは見えにくい全体像も押さえられる
- **不採用の理由:**
  - 画面一覧+遷移図のみ: 全体構造は見えるが「実際の操作感」が伝わりにくく、的確なフィードバックが難しい
  - ASCII ワイヤーフレーム: レイアウトの議論に引きずられやすい。この段階で詰めたいのは見た目ではなく操作の流れ
  - 選択肢提示型のみ: 比較しやすいが、選択肢にない発想が出にくい

## 2026-03-20: S1 の操作フローを C 案（URL 保存→詳細画面遷移）に決定

- **背景:** S1（曲を記録する）の操作フローとして、3つの案を比較検討した
  - A 案: URL 欄だけが目立ち、他フィールドは折りたたみで展開
  - B 案: 全フィールドが最初から表示
  - C 案: URL 入力で即保存→詳細入力画面に遷移。詳細不要ならすぐ戻れる
- **決定:** C 案を採用（初期設計。後から A/B に変更可能）
- **理由:**
  - 即時キャプチャの認知負荷が A と同等に低い（URL 欄だけ見える）
  - 即時→じっくりの移行が最も自然。保存完了後に「ついでに詳細も入れる？」という流れになり、事前の判断が不要
  - 詳細画面を S3（編集）と共用できるため、画面の再利用性が高い
  - A/B への変更は局所的で済む（詳細画面は S3 で残るため無駄にならない）

## 2026-03-20: 詳細画面の保存方式を「戻る操作トリガー + 確認ダイアログ」に決定

- **背景:** 詳細画面で入力した内容の保存タイミングをどうするか検討した
- **決定:** 「戻る」操作が保存のトリガーを兼ねる。変更がある状態で「戻る」を実行すると確認ダイアログを表示する。「保存」ボタンと「戻る」ボタンを併置しない
- **理由:**
  - ユーザーが考えるのは「用事が済んだら戻る」だけ。操作が最もシンプル
  - 保存と戻るが並ぶと「保存してから戻る？ 戻るだけ？」の判断が毎回発生する
  - 入力フィールドが少なく短文のため、途中保存の必要性がない
- **確認ダイアログの安全設計:** 危険な操作（破棄）と安全な操作（保存）を同じダイアログに並べない。操作ミスでも安全な結果になるよう設計する。詳細は `docs/ui-principles.md`（作成予定）に記載
- **実装方法:** 未確定（初期設計）。`beforeunload` は仮実装としてはありだが体験が良くないため変更前提

## 2026-03-20: UI 設計原則を別ドキュメント（ui-principles.md）に分離する決定

- **背景:** 確認ダイアログの安全設計を検討する中で、画面構成の設計（design.md）とは性質の異なる「UI の振る舞いの原則」を明文化する必要が出た。design.md に追記するか、別ドキュメントにするかを検討した
- **決定:** `docs/ui-principles.md` を新設する
- **理由:**
  - design.md は「何を作るか」の具体的な設計、ui-principles.md は「どう振る舞うべきか」の横断的な原則。性質が異なる
  - 原則は S1 だけでなく S3（削除）など他のストーリーにも適用される。画面構成から独立した参照先がある方が整理しやすい
  - 現時点のルール数は少ないが、シナリオウォークスルーの中で増えていく見込みがある

## 2026-03-20: シナリオウォークスルーの振り返りによるプロセス改善

- **背景:** S1 のシナリオウォークスルーを実施した後、やり取りを振り返り、進め方の問題点を洗い出した
- **発見した問題と対応:**
