# 意思決定ログ

設計判断やフェーズ移行の決定と、その理由を時系列で記録する。

## 2026-02-28: ニーズ整理フェーズの完了 → ユーザーストーリー作成へ移行

- **背景:** `docs/user-needs.md` を作成し、課題・ニーズ・JTBD・ペインポイントを整理した。次のステップ（ユーザーストーリー作成）に進めるかを判断する必要があった
- **決定:** ニーズ整理は完了とし、ユーザーストーリー作成に進む
- **理由:** `docs/process.md` のチェックリスト2項目を満たしている。課題は具体的に言語化されており、「やりたいこと」は行動レベルで記述されている。一部曖昧な箇所（振り返りからの外部サービス連携の範囲）はあるが、ユーザーストーリー作成の過程で具体化できる粒度であり、ニーズ整理の段階でこれ以上詰めると仕様策定との区別がなくなる

## 2026-02-28: 意思決定の記録方法を決定

- **背景:** フェーズ移行や設計判断を記録する手段が必要だった。選択肢として、ADR（1決定1ファイル）、単一ログファイル、git コミットログのみ、の3つを検討した
- **決定:** `docs/decisions.md` に時系列で追記する方式を採用。フェーズの進捗状況は `docs/process.md` のチェックリストで管理し、役割を分担する
- **理由:** 個人開発の頻度（週数回）では1決定1ファイルの ADR は摩擦が大きい。単一ファイルなら開けば全決定を一覧でき、肥大化の心配も当面ない。git コミットログだけでは「今どういう判断に基づいて進んでいるか」の一覧性がない

## 2026-03-05: 企画・設計フェーズのステップ構成を修正

- **背景:** ニーズ整理完了後、ユーザーストーリー → 優先順位 → 技術選定・設計 → 実装、という直列の計画を立てたが、批判的に再検討した結果、いくつかの問題が見つかった
- **問題点:**
  1. 「技術選定・設計」ステップにデータモデル・画面構成・技術スタックが混在しており、性質の異なる検討が雑居していた
  2. 画面構成・操作フローの検討が完全に欠落していた。記録・検索アプリでは「どんな画面でどう操作するか」がないと受け入れ条件も実装も具体化できない
  3. ユーザーストーリーの受け入れ条件を設計前に確定させる順序になっていたが、具体的な条件を書くには画面やデータ構造の概念が必要（鶏と卵の問題）
  4. URL メタデータ自動取得の技術的実現可能性の検証が抜けていた
- **決定:** ステップ構成を以下のように修正した
  1. ユーザーストーリー作成（ラフ。受け入れ条件は仮置き）
  2. ストーリーの優先順位づけ・MVP 範囲決定
  3. 設計（3つのサブステップ: データモデル / 画面構成・操作フロー / 技術スタック選定）
  4. 受け入れ条件の具体化（設計を反映してストーリーを仕上げる）
  5. タスク分解・実装
- **理由:** データモデルと画面構成は「何を作るか」の具体化、技術スタックは「どう作るか」の話であり、分けて扱うべき。また、設計結果をストーリーにフィードバックするステップを明示することで、鶏と卵の問題を解消する。個人開発なので正式なワイヤーフレームや API 設計書は不要だが、データモデル・画面構成・技術リスクの検証は明示的に行う

## 2026-03-05: ユーザーストーリー作成（ラフ）完了 → 優先順位づけへ移行

- **背景:** `docs/user-stories.md` に10件のストーリーを作成した。ストーリーマッピング（軽量版）を行い、ユーザーの行動フローに沿って抜け漏れを確認した
- **決定:** ユーザーストーリー（ラフ）は完了とし、優先順位づけ・MVP 範囲決定に進む
- **ステップ移行レビュー結果:**
  - 問1（成果物品質）: 全10ストーリーが実装可能な行動単位になっている。クライテリア OK
  - 問2（理解の変化）: 3点変わった
    1. 記録行動は「出会い→調べる→関心増幅→記録」の段階を経る（衝動的ではない）
    2. PC ブラウザが主戦場。スマホは MVP 対象外でよい
    3. SNS（Facebook）は併用。双方向のデータの流れがある（取り込み・投稿）
  - 問3（計画の修正）: 不要。理解の変化は user-needs.md と user-stories.md に反映済み。ステップ構成の変更は不要
- **理由:** チェックリストを満たしており、ストーリーマッピングで発見した不明点（利用シーン・SNS関係・過去データ）もすべてユーザーに確認して反映済み

## 2026-03-15: 記録行動の2パターンを発見 → S1・S2 を更新

- **背景:** 優先順位づけの過程で「S2（URL 自動取得）を MVP から外すと手動入力が面倒で使われないのでは？」という懸念が出た。ユーザーに確認したところ、新しいワークフローが判明した
- **発見:** 記録行動には2パターンある
  1. **即時キャプチャ:** 出会いの瞬間に URL だけさっと保存。曲名・アーティスト名は後回し
  2. **じっくり記録:** 調べた後に詳細も含めて記録する
- **決定:** S1 の必須項目を URL のみに変更。S2 に未補完レコードの一括自動取得を追加。user-needs.md に2パターンの記録行動を追記
- **理由:** URL のみで保存可能にすることで S1 の摩擦が大幅に下がり、S2 なしでも MVP が成立する。ユーザーは数日後や週末にまとめて情報整理する運用を許容している

## 2026-03-15: 優先順位づけ・MVP 範囲の決定 → 設計へ移行

- **背景:** 全10ストーリーの優先順位をつけ、MVP に含める範囲を決める必要があった
- **決定:** MVP は S1（記録）、S3（編集・削除）、S4（一覧）、S8（リンクから再生）の4ストーリー。S2（URL 自動取得）は次期の最優先とする
- **判断軸:** ペインの大きさ、利用頻度、依存関係、実装コストの4軸で評価
- **理由:**
  - S1 + S3 + S4 + S8 で「記録→一覧→振り返り→再リスニング」の基本サイクルが回る
  - S1 が URL のみで保存可能になったため、S2 なしでも MVP の摩擦は許容範囲内
  - 検索系（S5〜S7）は記録数が少ないうちは一覧の目視で代替可能
  - S9（Facebook 取込）は新規記録の基盤が先にあるべき。S10 はオプショナル
- **前提・仮定:**
  - MVP は新規記録の基盤。過去 Facebook データは後から取り込む
  - タグは検索機能がなくても「つけておく」だけで分類の価値がある
  - S2 は MVP 運用開始後、未補完レコードが溜まる前に早めに実装する
- **ステップ移行レビュー:**
  - 問0（整合性）: user-needs.md（即時キャプチャの追記）、user-stories.md（S1 の必須項目変更・優先順位セクション追加）、decisions.md の記載間で整合性を確認済み。齟齬なし
  - 問1（成果物品質）: 全ストーリーに優先度がつき、MVP 範囲が明確。クライテリア OK
  - 問2（理解の変化）: 記録行動に「即時キャプチャ」パターンがあることが判明し、S1・S2 の設計前提が変わった。user-needs.md と user-stories.md に反映済み
  - 問3（計画の修正）: ステップ移行時レビューに問0（整合性検査）を追加（下記エントリ参照）

## 2026-03-15: ステップ移行時レビューに問0（整合性検査）を追加

- **背景:** 優先順位づけの過程で、S1・S2 の部分更新を行った。AI がドキュメントを部分更新する際、直前の対話を過度に重視して全体の整合性が崩れるリスクがあることをユーザーが指摘した
- **決定:** ステップ移行時レビューに問0「成果物の整合性は保たれているか？」を追加。問1（クライテリア検査）の前提として、ドキュメント内の一貫性・構成の粒度、およびドキュメント間の矛盾・齟齬がないかを確認する
- **理由:** 既存の問1〜問3はいずれもこの観点をカバーしていなかった。全ステップ移行に共通する検査であるため、各ステップのチェックリストではなくレビューの共通手順に配置する。プロセス原則の「手戻りを減らすこと」に直結し、「過剰な管理をしない」原則とも矛盾しない（ドキュメントが少量の現時点では確認コストが低い）
