# 設計

MVP ストーリー（S1, S3, S4, S8）を実現するための設計。段階的に書き足していく。

---

## データモデル

### Record（音楽記録）

| フィールド | 型 | 必須 | 説明 |
|-----------|-----|------|------|
| id | integer (PK) | auto | 主キー、自動採番 |
| url | text | ✓ | 曲の URL（YouTube, Spotify 等）。一意制約なし（後述） |
| title | text | | 曲名。即時キャプチャ時は空 |
| artist | text | | アーティスト名。即時キャプチャ時は空 |
| memo | text | | ひとことメモ |
| created_at | datetime | auto | 記録日時（UTC） |
| updated_at | datetime | auto | 最終更新日時（UTC） |

**URL の設計方針:**
- **一意制約をつけない。** 同じ曲に再び出会ったとき「またこの曲に出会った」ことを日付とともに別レコードとして記録するため
- **可変。** リンク切れ時にユーザーが手動で別の URL に貼り替えることがある。ナチュラルキーにはしない（integer PK で識別）

**単一テーブル方針:**
Song テーブルと Encounter テーブルへの分割を検討し、不採用とした。「同じ曲」の同定がシステムでは困難なこと、MVP の CRUD が複雑化すること、再遭遇が稀であることが理由。再遭遇は UI 側で対応する（URL 入力時に既存レコードの通知）。詳細は [decisions.md](decisions.md) 参照。

### Tag（タグ）

タグは Record に対して複数付与可能。**別テーブル方式（中間テーブルなし）** を採用。

```
tags テーブル:
  id         integer (PK, auto)
  record_id  integer (FK → records.id)
  name       text    -- 正規化済みのタグ名
```

**正規化ルール:**
- 保存時に以下を順に適用:
  1. trim（前後の空白除去）
  2. NFKC 正規化（全角英数 → 半角、互換文字の統一。例: `Ｊａｚｚ` → `Jazz`、`㈱` → `(株)`）
  3. lowercase（ASCII/Latin 部分の小文字化。例: `Jazz` → `jazz`）
- これにより `Jazz` / `jazz` / ` jazz ` / `Ｊａｚｚ` の表記ゆれを自動吸収
- カタカナ ↔ ひらがなの変換は行わない（「ジャズ」と「じゃず」は意味的ニュアンスが異なり、ユーザーの意図を尊重する）
- 入力時の既存タグ候補表示は S7（タグ検索）と合わせて次期で実装

**この方式を選んだ理由:** JSON 配列やカンマ区切りは実装が最小だが、次期の S7（タグ検索）で構造変更が必要になる。別テーブルなら `WHERE name = ?` で効率的に絞り込める。中間テーブル付きの完全正規化（タグマスタ）は個人ツールには過剰。詳細は [decisions.md](decisions.md) 参照。

## 検索方針

MVP ではタグ検索・メモ検索（S7）は範囲外。次期での実装方針を先に定めておく。

### 方針: 完全一致 + FTS5（trigram トークナイザ）。ベクトル検索は不採用

| 検索対象 | 方式 | 理由 |
|---------|------|------|
| タグ | 正規化済みタグの完全一致 | 短い単語の一致問題。正規化で Recall を確保しつつ Precision を維持 |
| メモ | SQLite FTS5（**trigram** トークナイザ） | 日本語の分かち書き不要。部分文字列マッチで漏れなく検索可能 |
| アーティスト名 | FTS5（trigram）または LIKE | 日本語アーティスト名の部分一致を確実にカバー |
| 曲名 | FTS5（trigram）または LIKE | 同上 |

### 日本語検索と trigram トークナイザ

FTS5 のデフォルトトークナイザ（unicode61）は空白・句読点でトークンを分割するため、分かち書きしない日本語テキストを正しくトークン化できない。この問題への対応として **trigram トークナイザ**を採用する。

**trigram トークナイザの仕組み:**
- テキストを3文字ずつの連続部分文字列（トライグラム）に分割してインデックスを構築する
- 例: `「椎名林檎」` → `椎名林`, `名林檎` の2トライグラム
- 検索クエリも同様にトライグラムに分解し、すべてのトライグラムを含む行をマッチさせる
- 言語に依存しないため、辞書や外部ライブラリが不要

**trigram を選んだ理由:**
1. **日本語が正しく検索できる。** 分かち書き不要で、部分文字列マッチとして機能する
2. **追加依存がない。** SQLite 3.34.0 以降の FTS5 に組み込み済み。ICU 拡張や MeCab 等の形態素解析器が不要で、ローカル実行の軽量さを維持できる
3. **英語も同時に扱える。** 日英混在テキスト（アーティスト名がローマ字表記の場合など）でも問題なく動作する

**制約と許容:**
- **最小クエリ長が3文字。** 1〜2文字での検索はヒットしない。ただし、日本語の実用的な検索語は3文字以上が大半（例: 「ジャズ」で3文字）。1〜2文字で検索したい場面（「AI」など）は LIKE フォールバックで対応可能
- **インデックスサイズがやや大きい。** ただし年間数百件のレコードでは無視できる規模
- **BM25 ランキングは使えない。** trigram は部分文字列マッチであり、TF-IDF ベースのランキングが意味を持たない。ただし、レコード数が少なく一覧で十分なため、ランキングの重要度は低い

### ベクトル検索（LLM 埋め込み）を不採用とした理由

1. **検索対象のテキストが短すぎる。** メモは「ひとこと」、タグは単語。短いテキストの埋め込みは情報量が少なく精度が低い
2. **レコード数が少なすぎる。** 週数回の記録で年間数百件。全件走査でも一瞬
3. **Precision の問題。** 意味的に「近い」結果が個人の音楽記録で有用とは限らない。明示的な検索のほうが結果を信頼できる
4. **運用の重さ。** ローカル実行と決めたのに、埋め込みモデル（API 依存 or ローカルモデルのメモリ消費）が増える
5. **ニーズが未確認。** 「雰囲気で探したい」という検索ニーズは現時点で挙がっていない

**再検討トリガー:** レコードが数千件に増え、かつ「雰囲気で探したい」ニーズが実際に発生したとき。埋め込みカラムの後付けは容易なので、データモデルへの影響はない。

### 日本語対応の既知の限界と再検討トリガー

現設計は「追加依存なし・軽量」を優先した実用的な選択であり、MVP〜次期の規模では十分と判断している。ただし以下の限界は運用開始後に摩擦が顕在化する可能性がある。実際に不満が出たらユーザーストーリーやバックログに反映し、アーキテクチャの見直しを検討する。

**1. trigram の最小3文字制約と短い日本語語彙**

2文字以下の実用的な検索語が存在する（アーティスト名「嵐」、ジャンル語「演歌」「洋楽」など）。タグは完全一致のため影響しないが、メモやアーティスト名の自由テキスト検索（FTS5）では trigram がヒットしない。設計上は LIKE フォールバックで対応可能としているが、「いつ FTS5 を使い、いつ LIKE にフォールバックするか」の判断ロジックが暗黙的に実装に委ねられている。

- **顕在化の条件:** 検索機能（S5〜S7）の実装時、および実運用で短い語での検索が頻繁に必要になったとき
- **対応の方向:** 実装時にフォールバック戦略を明示的に設計する（例: クエリ長 < 3 なら自動で LIKE に切り替え）。それでも不十分なら trigram 以外のトークナイザを再検討

**2. カタカナ ↔ ひらがなの不一致**

「ジャズ」でタグ付けした記録を「じゃず」で検索しても見つからない。タグの候補表示（次期 S7）で入力時の不一致は緩和できるが、メモの自由テキスト検索では同じ問題が残る。

- **顕在化の条件:** 検索時に「見つかるはずの記録が見つからない」体験が繰り返し発生したとき
- **対応の方向:** 検索クエリ側でカタカナ ↔ ひらがなの展開（両方で検索して OR 結合）を検討。保存時の正規化ではなく検索時の展開で対応するほうが、既存データへの影響がない

**3. 同一アーティストの表記バリエーション（エイリアス問題）**

「YOASOBI」と「ヨアソビ」、「King Gnu」と「キングヌー」は文字列として完全に異なり、正規化では吸収できない。これは表記ゆれではなくエイリアスの問題であり、現設計はこの問題に対する仕組みを持っていない。

- **顕在化の条件:** 記録数が増え、同一アーティストが複数の表記で記録されていることにユーザーが気づき、統一的に検索したいと感じたとき
- **対応の方向:** アーティストのエイリアス管理（名寄せ）の仕組みが必要。手動マッピング（UI でアーティストを紐づける）か、外部音楽データベース（MusicBrainz 等）との連携が選択肢になる。データモデルの拡張（アーティストテーブルの分離）を伴う可能性がある

**4. trigram の偽陽性（ノイズ）**

trigram は部分文字列マッチのため、意図しない記録がヒットする可能性がある。レコード数が少ないうちは目視で除外できるが、増えるとノイズが検索体験を損なう。

- **顕在化の条件:** レコードが数百件を超え、検索結果に無関係な記録が混じることが気になり始めたとき
- **対応の方向:** 形態素解析ベースのトークナイザ（MeCab + SQLite FTS5 カスタムトークナイザ、または Lindera 等の Rust 製形態素解析器）への移行を検討。辞書管理の運用コストとのトレードオフ
