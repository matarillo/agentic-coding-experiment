# 開発プロセス

このプロジェクトにおける、ユーザー（自分）と Claude による開発の進め方を記録する。

## 全体の流れ

```
企画・設計フェーズ                          実装フェーズ
──────────────────────────────────        ──────────────────────
1. ニーズ整理                               タスク分解
    ↓                                          ↓
2. ユーザーストーリー作成（ラフ）             Issue 作成・実装
    ↓                                          ↓
3. 優先順位づけ・MVP 範囲決定               動作確認・フィードバック
    ↓
4. 設計（データモデル / 画面 / 技術スタック）
    ↓
5. 受け入れ条件の具体化

※ 各ステップの移行時にレビューを行う（後述）
```

---

## 企画・設計フェーズ

### ステップと作成物

| ステップ | 作成物 | 説明 |
|----------|--------|------|
| 1. ニーズ整理 | `docs/user-needs.md` | ユーザーの課題・やりたいことを整理する。JTBD やペインポイントの分析を含む |
| 2. ユーザーストーリー作成（ラフ） | `docs/user-stories.md` | ニーズを具体的なシナリオに落とし込む。受け入れ条件は仮置き |
| 3. 優先順位づけ・MVP 範囲決定 | `docs/user-stories.md` に追記 | ストーリーに優先度をつけ、MVP に含める範囲を決める |
| 4. 設計 | `docs/design.md` | 3つのサブステップで進める（下記参照） |
| 5. 受け入れ条件の具体化 | `docs/user-stories.md` を更新 | 設計結果を反映してストーリーの受け入れ条件を仕上げる |

**Step 4（設計）のサブステップ:**

| サブステップ | 内容 |
|-------------|------|
| 4a. データモデル設計 | 何をどう保存するか。フィールド、関連、タグの扱いなど |
| 4b. 画面構成・操作フロー | どんな画面があり、どう遷移するか。ラフな画面リストと操作の流れ |
| 4c. 技術スタック選定 | 言語、FW、DB、デプロイ形態。URL メタデータ取得の実現可能性調査を含む |

### 次のステップに進むためのチェックリスト

**ニーズ整理 → ユーザーストーリー（ラフ）:**
- [x] 解決したい課題が具体的に言語化されている
- [x] 「やりたいこと」が抽象的な願望ではなく、行動として書かれている

**ユーザーストーリー → 優先順位づけ:**
- [ ] ストーリーが「実装可能な行動単位」になっている

**優先順位づけ → 設計:**
- [ ] ストーリーの優先順位がついている（全部一度にはやらない）
- [ ] MVP に含めるストーリーが決まっている

**設計 → 受け入れ条件の具体化:**
- [ ] データモデルが定義されている
- [ ] 画面構成と主要な操作フローが決まっている
- [ ] 技術スタックが決まっている

**受け入れ条件の具体化 → 実装開始:**
- [ ] MVP ストーリーの受け入れ条件が設計と整合している
- [ ] 開発環境が動く状態にある

### ステップ移行時レビュー

各ステップの完了時、次に進む前に以下の3問を確認する。チェックリスト（上記）が「成果物の品質検査」であるのに対し、このレビューは「計画自体の検査」を行う。

| # | 問い | 判断の対象 |
|---|------|-----------|
| 1 | 成果物はクライテリアを満たしているか？ | 今のステップのアウトプット品質 |
| 2 | このステップで、ゴールや前提についての理解が変わったか？ | ニーズ理解・スコープ・前提条件 |
| 3 | 残りのステップやクライテリアを修正すべきか？ | プロセス・計画そのもの |

- 問1はシングルループ（作業の検査）、問2・3はダブルループ（計画の検査）
- 修正が必要と判断した場合は `docs/decisions.md` に記録してからプロセスを更新する

## 実装フェーズ

### 進め方

1. **タスク分解:** ユーザーストーリー1つを実装可能な単位に分解する
2. **Issue 作成:** GitHub Issue として登録する（1 Issue = 数時間〜1日で終わる粒度）
3. **実装:** ブランチを切って実装する。Claude と対話しながら進める
4. **動作確認:** 動くものを確認してからマージする
5. **フィードバック:** 使ってみて気づいたことを次のストーリーや Issue に反映する

### 作成物

| 作成物 | 場所 | 説明 |
|--------|------|------|
| タスク（Issue） | GitHub Issues | ユーザーストーリーから分解した実装タスク |
| コード | リポジトリ本体 | ブランチ → PR → マージで管理 |
| 設計メモ（必要な場合） | `docs/` 配下 | 実装中に判明した設計判断を記録する |
| 意思決定ログ | `docs/decisions.md` | 設計判断やフェーズ移行の決定と理由を時系列で記録する |

### 1つのストーリーが完了したと言えるチェックリスト

- [ ] ユーザーストーリーの受け入れ条件を満たしている
- [ ] 自分で使ってみて違和感がない

## セッション運用

- 対話セッションが長くなったら、区切りの良いところで終了し新しいセッションを始める
- **セッション終了時に `CLAUDE.md` の「現在のステータス」セクションを更新する。** 次のセッションのエージェントが文脈を即座に掴めるようにする
- ステータスには「今どのフェーズにいるか」と「次にやること」を書く

---

## 原則

- **ドキュメントは生き物。** 進めながら更新する。完璧に書いてから次に進む必要はない
- **小さく作って早く使う。** 全機能を設計してから実装に入るのではなく、最小限のストーリーから実装を始める
- **過剰な管理をしない。** 一人開発なので、プロセスの目的は「忘れないこと」と「手戻りを減らすこと」
