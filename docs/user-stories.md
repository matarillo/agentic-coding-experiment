# ユーザーストーリー

`docs/user-needs.md` をもとに作成。受け入れ条件は仮置き（設計後に具体化する）。

## 優先順位・MVP 範囲

### 判断軸

| 軸 | 説明 |
|----|------|
| ペインの大きさ | 「記録がなくて振り返れない」問題を直接解決するか |
| 利用頻度 | 日常的に使うか、たまにしか使わないか |
| 依存関係 | 他のストーリーの前提になるか |
| 実装コスト | 外部 API 連携や複雑な UI が必要か |

### MVP（最初のリリースに含める）

| ストーリー | 理由 |
|-----------|------|
| S1: 曲を記録する | コア機能。URL のみで保存できるため摩擦が低い |
| S3: 記録を編集・削除する | 即時キャプチャ後の補完（曲名・タグ追加）に必須 |
| S4: 記録を一覧で見る | 記録しても見返せないと意味がない |
| S8: 記録から曲を聴く | URL リンクだけなので低コスト。振り返り→再リスニングの導線 |

### 次期（MVP 直後に優先的に実装）

| ストーリー | 理由 |
|-----------|------|
| S2: URL から情報を自動取得 | 即時キャプチャで溜まった未補完レコードの整理に必要。MVP 運用が続くと早期に必要になる |
| S5: 日付で振り返る | 記録が増えてくると一覧の目視では不十分になる |
| S6: アーティストで探す | 同上 |
| S7: タグ・キーワードで探す | 同上。MVP でタグをつけておき、検索は次期で実装 |

### 将来（必要性を見てから判断）

| ストーリー | 理由 |
|-----------|------|
| S9: Facebook から取り込む | 価値は高いが API 連携が重い。MVP は新規記録の基盤として十分機能する |
| S10: SNS に投稿する | オプショナルと位置づけ済み |

### MVP の前提・仮定

- MVP は「今日以降の新しい出会い」を記録する基盤。過去の Facebook データの取り込みは基盤ができた後に行う
- 記録数が少ないうちは一覧の目視で十分。タグは将来の検索に備えてつけておくだけで価値がある
- S2（URL 自動取得）がないと未補完レコードが溜まるため、MVP リリース後に早めに実装する

## S1: 曲を記録する

**ストーリー:**
音楽好きのユーザーとして、新しい曲に出会ったときに、PC ブラウザからさっと記録したい。なぜなら、後から振り返れるようにしたいから。

**背景:** 記録には2つのパターンがある。(1) 出会いの瞬間に URL だけさっと保存する「即時キャプチャ」と、(2) アーティスト情報を調べた後に詳細も含めて記録する「じっくり記録」。どちらのパターンでも最小限の手間で保存できることが重要。

**記録する情報:**
- URL（YouTube, ブログ記事, Wikipedia など）— 必須
- 曲名（任意。後から補完可）
- アーティスト名（任意。後から補完可）
- ひとことメモ（任意）
- タグ（任意、複数可）
- 記録日時（自動）

**仮の受け入れ条件:**
- [ ] PC ブラウザから URL を入力して保存できる（URL のみで保存可能）
- [ ] 曲名・アーティスト名・メモ・タグは空でも保存できる
- [ ] 記録日時は自動で付与される

---

## S2: URL から情報を自動取得する

**ストーリー:**
ユーザーとして、URL を貼るだけで曲名やアーティスト名が自動入力されてほしい。なぜなら、すでにブラウザで開いている URL をコピペするだけで済ませたいから。

**背景:** 記録時点ではブラウザで YouTube 動画ページやアーティスト紹介記事を開いていることが多い。YouTube URL からの自動取得が最も利用頻度が高いと想定。また、即時キャプチャ（URL のみ保存）した記録を後からまとめて補完するユースケースもある。

**仮の受け入れ条件:**
- [ ] YouTube の URL を入力すると、曲名・アーティスト名が自動で取得される
- [ ] 自動取得された情報は手動で修正できる
- [ ] URL が対応外の場合は手動入力にフォールバックする
- [ ] 曲名・アーティスト名が未補完のレコードを一覧し、一括で自動取得を実行できる

---

## S3: 記録を編集・削除する

**ストーリー:**
ユーザーとして、過去に記録した内容を後から編集・削除したい。なぜなら、タグを追加したり、メモを書き直したりすることがあるから。

**仮の受け入れ条件:**
- [ ] 既存の記録の全フィールドを編集できる
- [ ] 記録を削除できる

---

## S4: 記録を一覧で見る

**ストーリー:**
ユーザーとして、記録した曲を一覧で見たい。なぜなら、自分のアーカイブを眺めて振り返りたいから。

**仮の受け入れ条件:**
- [ ] 記録が新しい順に一覧表示される
- [ ] 一覧から個別の記録の詳細を見られる

---

## S5: 日付で振り返る

**ストーリー:**
ユーザーとして、日付や期間を指定して記録を絞り込みたい。なぜなら、「あの時期何を聴いていたか」を振り返りたいから。

**仮の受け入れ条件:**
- [ ] 期間を指定して記録を絞り込める

---

## S6: アーティストで探す

**ストーリー:**
ユーザーとして、アーティスト名で記録を検索したい。なぜなら、「このアーティストの曲で記録したものは何があったか」を知りたいから。

**仮の受け入れ条件:**
- [ ] アーティスト名で記録を絞り込める

---

## S7: タグ・キーワードで探す

**ストーリー:**
ユーザーとして、タグやキーワードで記録を検索したい。なぜなら、「作業BGMに良かった曲」のように気分やシーンで探したいから。

**仮の受け入れ条件:**
- [ ] タグで記録を絞り込める
- [ ] メモの内容でも検索できる

---

## S8: 記録から曲を聴く

**ストーリー:**
ユーザーとして、記録した曲の URL をクリックして元のサービスで再生したい。なぜなら、振り返りからすぐにリスニング体験に戻りたいから。

**仮の受け入れ条件:**
- [ ] 記録に含まれる URL がリンクとして機能し、外部サービスで開ける

---

## S9: Facebook の投稿から記録を取り込む

**ストーリー:**
ユーザーとして、過去に Facebook に投稿した音楽リンクをこのアプリに取り込みたい。なぜなら、これまで蓄積してきた出会いの記録をアーカイブに含めたいから。

**背景:** 過去の音楽リンク投稿は主に Facebook に蓄積されている。また、今後もこのアプリを経由せず直接 Facebook に投稿することがあるため、継続的に取り込む手段もほしい。

**仮の受け入れ条件:**
- [ ] Facebook の過去投稿から音楽リンクを含む投稿を抽出し、記録として取り込める
- [ ] 取り込んだ記録は手動で編集できる（タグ追加など）
- [ ] 初回の一括取り込みだけでなく、後からの追加取り込みもできる

---

## S10: 記録時に SNS にも投稿する（オプショナル）

**ストーリー:**
ユーザーとして、このアプリで曲を記録するときに、同時に SNS にも投稿できると嬉しい。なぜなら、記録と共有を別々にやるのは二度手間だから。

**仮の受け入れ条件:**
- [ ] 記録保存時に SNS への投稿を選択できる（任意）
- [ ] 投稿しなくても記録は保存できる
